# CreditTransfer-First Execution Plan

## Status

The owner approved this delivery direction and activated its bounded execution sequence on 2026-08-16. CreditTransfer
is the primary whole-solution acceptance target; other supplied and open-source applications remain generalization,
regression, and false-positive evidence. Durable execution state identifies the one active checkpoint.

## Outcome

Produce useful, evidence-backed diagrams for the entire CreditTransfer solution as quickly as practical. Initial
labels may remain technical or code-like when they are accurate and understandable. Natural-language refinement is
later work and must not delay useful diagrams.

CreditTransfer drives capability priority, never production matching rules. Application, route, type, method, and
business names remain outside generic analyzers and framework models.

`docs/project/diagram-strategy.md` defines the target diagram philosophy and accelerated short-, medium-, long-, and
very-long-term capability horizons. The historical CreditTransfer diagrams numbered 1–12 inspire decomposition and
uncertainty presentation only; the current buildable solution remains behavioral authority.

## Bounded sequence

1. **Admission baseline.** Verify the external solution safely, freeze executable entries and exclusions, run the
   current product, and record complete/useful, partial, diagnostic-only, and uncovered behavior.
2. **Predicate and terminal topology.** Replace supported generic condition and termination labels with exact
   compiler-evidenced expressions, `Otherwise`, early terminals, and supported rejoins so guarded calls can render.
3. **Generic traversal foundation.** Add configurable exact roots and bounded `DirectExact` source-call traversal
   with cycle, depth, node, profile, and source-availability boundaries.
4. **Multi-project source traversal.** Follow compatible source bodies across project references without mixing
   compilation profiles or target frameworks.
5. **First useful technical suite.** Regenerate context, adapter, facade, engine, worker/recovery, and boundary views.
   Keep generated-client calls external until exact contract evidence proves a client/service relationship.
6. **High-value framework expansion.** Add generic CoreWCF/WCF contracts and dispatch, EF6/EDMX persistence,
   background/recovery flows, outbound SOAP/HTTP boundaries, exception/outcome propagation, and only the narrow DI
   subset demanded by exact composition evidence.
7. **Automatic decomposition and whole-solution acceptance.** Split overview and child flows from generic complexity,
   participant, call-depth, repeated-subflow, and state-transition facts; account for every admitted root honestly.
8. **Generalization and later horizons.** Run unrelated corpus regressions throughout, then add cross-root linking,
   state-machine views, persistence/incremental behavior, explanation/search, performance/platform evidence, release
   hardening, and natural-language/visual refinement after the primary diagrams are useful.

## Delivery discipline

- Approve the sequence as a bounded run, but keep one semantic boundary per checkpoint and one active checkpoint.
- Avoid ceremony-only slices, duplicate tests, broad full-suite reruns, and premature wording work.
- Use the least expensive reliable test layer and one proportionate final gate per checkpoint.
- Produce and inspect improved CreditTransfer output at every user-visible milestone rather than waiting for the
  whole solution.
- Require a generic fixture plus unrelated positive or negative evidence for every reusable semantic capability.
- Push at stable, reviewed points after focused verification; never push external source, configuration secrets,
  build output, or raw session material.

## Initial acceptance ladder

The first useful technical suite should establish these independently provable views before deeper framework
correlation:

1. HTTP request handling to a generated SOAP-client boundary.
2. CoreWCF service operation through the business engine.
3. Background-service processing through recovery/retry behavior.
4. Solution/process context with explicit external and missing boundaries.
5. Main engine orchestration split into linked child flows when complexity exceeds the diagram budget.

Later exact contract evidence may connect client and service views. Until then, separate truthful diagrams are better
than a falsely complete end-to-end flow.
