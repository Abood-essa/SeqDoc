# CreditTransfer-First Execution Plan

## Status

The owner approved this delivery direction on 2026-08-16. Product execution remains idle until explicit activation.
CreditTransfer is the primary whole-solution acceptance target; other supplied and open-source applications remain
generalization, regression, and false-positive evidence.

## Outcome

Produce useful, evidence-backed diagrams for the entire CreditTransfer solution as quickly as practical. Initial
labels may remain technical or code-like when they are accurate and understandable. Natural-language refinement is
later work and must not delay useful diagrams.

CreditTransfer drives capability priority, never production matching rules. Application, route, type, method, and
business names remain outside generic analyzers and framework models.

## Bounded sequence

1. **Admission baseline.** Verify the external solution safely, freeze executable entries and exclusions, run the
   current product, and record complete/useful, partial, diagnostic-only, and uncovered behavior.
2. **Predicate and branch presentation.** Replace supported generic condition and termination labels with exact
   compiler-evidenced expressions, `Otherwise`, returns, and outcomes. Ambiguous mappings remain explicit.
3. **Generic traversal foundation.** Add configurable exact roots, then bounded exact-call traversal with cycle,
   depth, node, profile, and source-availability boundaries.
4. **Multi-project source traversal.** Follow compatible source bodies across project references without mixing
   compilation profiles or target frameworks.
5. **First useful diagram milestone.** Regenerate CreditTransfer immediately and review actual Markdown/Mermaid.
   Keep generated-client calls as external boundaries until contract identity proves a client/service relationship.
6. **High-value framework expansion.** Add generic CoreWCF/WCF contracts and dispatch, EF6/EDMX persistence,
   background/recovery flows, outbound SOAP/HTTP boundaries, and exception/outcome propagation in measured-value
   order. Add only the narrow conventional Microsoft DI subset demanded by exact composition evidence.
7. **Whole-solution acceptance.** Cover every admitted HTTP, service, worker, data, and external-system flow; report
   every remaining unsupported boundary honestly.
8. **Generalization and later horizons.** Run unrelated corpus regressions throughout. Broaden framework coverage,
   persistence/incremental behavior, explanation/search, performance/platform evidence, release hardening, and
   natural-language refinement after the primary diagrams are useful.

## Delivery discipline

- Approve the sequence as a bounded run, but keep one semantic boundary per checkpoint and one active checkpoint.
- Avoid ceremony-only slices, duplicate tests, broad full-suite reruns, and premature wording work.
- Use the least expensive reliable test layer and one proportionate final gate per checkpoint.
- Produce and inspect improved CreditTransfer output at every user-visible milestone rather than waiting for the
  whole solution.
- Require a generic fixture plus unrelated positive or negative evidence for every reusable semantic capability.
- Push at stable, reviewed points after focused verification; never push external source, configuration secrets,
  build output, or raw session material.

## Initial acceptance ladder

The first diagrams should establish these independently provable views before deeper framework correlation:

1. HTTP request handling to a generated SOAP-client boundary.
2. CoreWCF service operation through the business engine.
3. Background-service processing through recovery/retry behavior.

Later exact contract evidence may connect client and service views. Until then, separate truthful diagrams are better
than a falsely complete end-to-end flow.
